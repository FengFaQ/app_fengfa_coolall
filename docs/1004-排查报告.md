## 二、参考项目的关键发现

### 2.1 人机验证只在写操作时触发

`err_request_captcha` 出现在：

| 文件 | 行 | 场景 |
| --- | --- | --- |
| `ReplyViewModel.kt` | 52 | 发评论 |
| `ReplyViewModel.kt` | 129 | 发回复 |
| `ReplyActivity.kt` | 601 | 请求验证参数 |

**浏览时遇到的是 1004，不是 `err_request_captcha`。**

### 2.2 参考项目对 1004 的分类

`ApiFailure.fromBody()` 的判定顺序：

```
1. status == -10 或含「网络环境」  → RISK_CONTROL
2. messageStatus == err_request_need_upgrade_new_version → CLIENT_UPGRADE
3. 含 "captcha" 或 "验证码"        → CAPTCHA
4. 含 "login"/"auth"/"登录"        → AUTHENTICATION
5. 含 "rate_limit"/"频繁"          → RATE_LIMIT
6. else                            → BUSINESS
```

纯 1004 的 clues = `" 请求验证错误 "`：
- 不含 `captcha`
- 不含 `验证码`（只有「验证」两个字）
- 不含 `login` / `频繁`

**所以走 else → BUSINESS。**

### 2.3 挑战识别条件

`CaptchaChallenge.from()` 要求：

```kotlin
body?.get("messageStatus")?.asString == "err_request_captcha_v2"
```

否则返回 `null`（不认为是挑战）。

`414e5c9b866a03db03f860a1a9101672` 在参考项目里**只是兜底**，
正常路径拿到的是服务端下发的真实 captchaId。

## 三、我犯的错误

### 3.1 错误假设

从最早的诊断开始，我就假设：

> `status: 1004` = 需要人机验证

**没有任何证据支持这个假设。**

### 3.2 错误后果链

```
纯 1004
 → classify() 判为 CaptchaNeeded
 → 用 CaptchaChallenge::default() 的硬编码 id "414e5c9b..."
 → 用别人的 captchaId 初始化易盾
 → 必然失败（那不是酷安给这个设备的挑战）
 → 验证窗口打不开
 → 用户看到「点了没反应」
```

### 3.3 已修正

- 删除 `if status == Some(1004) { CaptchaNeeded }`
- 关键词从「验证」收紧为「验证码」
- 本地错误不再借用 1004 标识

## 四、当前的真实处境

去掉错误的验证码映射后，用户看到的是：

```
请求失败，服务端返回：请求验证错误
```

**这比弹一个打不开的验证窗口诚实**，但浏览仍然不可用。

### 未解的问题

1004 到底是什么？

可能的解释（都未验证）：

| 假设 | 支持证据 | 反对证据 |
| --- | --- | --- |
| A. 需要登录 | 所有端点都拦，包括 checkLoginInfo | 手机上的 c001apk 未登录能浏览 |
| B. 需要真实数盟 ID | 设备串改了没用 | 无法验证（没有真实 ID） |
| C. 需要过 WAF 的完整挑战 | 指纹对了才 200 | 已拿到 200 |
| D. 服务端对这个 IP/时段有额外限制 | — | 无法验证 |

**注意**：手机上的 c001apk 能正常浏览（用户已确认），说明 1004 不是无解的，
只是我们还缺某个关键条件。

## 五、下一步建议

### 5.1 最直接的验证方法

**抓一次手机端 c001apk 的真实请求。**
对比它的请求头与我们生成的差异，特别是：

- `X-App-Device` 的完整值（9 段里的 szlmId 长得什么样）
- `X-App-Token` 的格式
- 是否有我们用到的头之外的额外头
- Cookie 里有什么

这是唯一能确定答案的方法。需要用户配合。

### 5.2 如果拿不到真机抓包

按可能性排序尝试：

1. 换协议版本（试 16.0.0 / 16.5.0 等其他 16.x）
2. 补更多请求头（参考 AddCookiesInterceptor 的完整列表）
3. 检查 TLS 指纹（reqwest 的 ClientHello 是否与 OkHttp 差异过大）

### 5.3 阶段 1 的现实选择

如果 1004 短期无法解决：

- 把「浏览」标记为阻塞，转做其他不依赖 API 的部分
- 或者降级为「公开页浏览」——但当前公开页路径也不可用
