# 1004 攻坚全记录

> 记录时间：2026-11-01 10:10
> 结论：**根因是 TokenV3 密码输入的 Base64 padding，其余 14 个方向全部不是根因。**
> 本文保留每一次排除的证据与当时的推理，供后续排查复用。

---

## 一、问题定义

所有酷安 API 请求返回：

```json
{"status":1004,"error":null,"message":"请求验证错误"}
```

而手机上的 c001apk v1.5.0（游客模式）能正常浏览。

---

## 二、根因（最终确认）

### 仓库 1 的正确实现（`TokenV3.kt`）

```kotlin
private fun base64(value: String) =
    encoder.withoutPadding().encodeToString(...)      // ← 去 padding，用于 source

fun create(device, appCode, timestamp): String {
    ...
    val plain = "com.coolapk.market&$segment&${md5(device)}&$time&$appCode"
    val password = md5(encoder.encodeToString(plain.toByteArray()))   // ← 保留 padding！
    val source = base64("${time.toString(16)}/${md5(plain)}").take(22) // ← 去 padding
    ...
}
```

### 我的错误

```rust
// 错误
let password = md5_hex(&b64_nopad(&plain));
let source_full = b64_nopad(&format!("{t:x}/{}", md5_hex(&plain)));
```

把 `withoutPadding` 也应用到了 **password 输入**上。
`plain` 长度 167 字节，`167 % 3 = 2`，Base64 编码必然产生 1 个 `=` padding。

### 修正

```rust
// 正确
let password = md5_hex(&STANDARD.encode(plain.as_bytes()));   // 保留 '='
let source_full = b64_nopad(&format!("{t:x}/{}", md5_hex(&plain)));
```

### 验证

| 修正前 | 修正后 |
| --- | --- |
| `1004 请求验证错误` | `HTTP 200 OK -> 成功！长度 221718` |

真机数据（meizu / MEIZU 21 / Android 16 / SDK 36）实测。

## 三、为什么这个错误极难发现

1. **Token 格式完全合法**：`v3` + 60 字节 bcrypt，结构校验全部通过
2. **服务端错误码不区分**：Token 错误和服务端风控都返回 1004
3. **只有两种措辞**：
   - Token 无效 → `请求未验证`
   - Token 格式对但内容错 → `请求验证错误`
   - **两者 status 都是 1004**
4. 我的自校验脚本和 Rust 实现**互相验证**，两个都错，所以「一致」不构成证据

> **教训**：交叉验证时，两个实现必须来自**独立的参考源**，
> 不能是「我照着自己的理解写两份」。

## 四、被排除的 14 个方向

### 1. IP / 网络被限

| 测试 | 结果 |
| --- | --- |
| 绑定 WLAN 网卡绕过 FlClash | 1004 |
| 直连真实 IP（119.188.175.46） | 1004 |

**结论**：不是 IP 问题。

### 2. 设备串格式

| 形态 | 结果 |
| --- | --- |
| 随机 32 位 hex | 1004 |
| 空 szlmId | 1004 |
| 全零 | 1004 |
| 20 位字母数字 | 1004 |
| 换华为机型 | 1004 |

**结论**：不是设备串格式。

### 3. 数盟 ID

已完整实现 `shuzilm.rs`（移植 DuClient/DuCodec），成功拿到服务端签发的真实 ID：

```
DUP4awltXU__0ABOiBz7NwkxTrv4hbvIeRgd
```

用真实 ID 仍 1004。

**结论**：不是数盟 ID。

### 4. SESSID

| 测试 | 结果 |
| --- | --- |
| 无 SESSID | 1004 |
| 服务端下发的 SESSID | 1004 |
| App 当前有效 SESSID | 1004 |

**结论**：不是会话问题。

### 5. 端点

首页 / 动态 / 搜索 / 用户 / checkLoginInfo —— 全部 1004。

**补充实验**：请求不存在的 `/v6/__nope__` 返回 `{"code":404}`，
说明 **1004 发生在路由之前**，是门禁层判定。

### 6. 请求头

逐个移除测试，所有必需头齐备。缺失 `X-Requested-With` 会变 1000。

**结论**：不是请求头缺失。

### 7. 协议版本

| 版本 | 结果 |
| --- | --- |
| 16.7.0 / 2610291 | 1004 |
| 16.2.0 / 2604201 | 1004 |
| 13.4.1 / 2312121 | 403 |

### 8. HTTP 层

gzip / HTTP1.1 / keep-alive / 模拟 OkHttp 默认头 —— 全 1004。

### 9. installTime / firstLaunch

| 参数 | 结果 |
| --- | --- |
| firstLaunch=0, installTime=0 | 1004 |
| firstLaunch=1, installTime=真实时间戳 | 1004 |

**结论**：参数正确但不影响 1004（仍是应该修的细节）。

### 10. curl_cffi 浏览器指纹

chrome110/120/124/131、safari15_5/17_0、firefox133 —— 全 1004。

### 11. Chromium / WebView

Edge 156 发请求得到 **403**（比 1004 拒得更早，CDN 层就拦）。

**有价值的副产品**：rustls 的 1004 比 Chromium 的 403「更靠里」，
说明 rustls 指纹反而更接近 App。

### 12. 手机 BoringSSL curl

同设备、同 BoringSSL 库，仅是配置差异：

| 项 | App (OkHttp) | curl (BoringSSL) |
| --- | --- | --- |
| 套件数 | 15 | 17 |
| 扩展顺序 | `0,23,65281,10,11,35,16,5,13,51,45,43,21` | `0,23,65281,10,11,16,13,51,45,43,21` |
| 结果 | 能看内容 | 1004 |

### 13. TLS 指纹完全对齐

用真机 ClientHello 模板（517 字节）+ 自生成 key_share，完成**完整 TLS 1.3 握手**：

```
ServerHello: suite=0x1302 hash=sha384
服务端 Finished 校验: 通过
HTTP/1.1 200 OK
{"status":1004,...}
```

**TLS 层完全通过，业务层仍 1004。**

关键参数（供复用）：
- ClientHello 总长 517 字节
- key_share 公钥偏移 **229**（record 内含 5 字节 header）
- 套件 0x1302 用 **SHA-384** 和 32 字节 key
- TLS 1.3 记录层 AEAD 的 **AAD 是记录头 5 字节**，不是空

### 14. UWP 的 TokenV3 算法

| 项 | C001 | UWP |
| --- | --- | --- |
| password | 保留 padding | 保留 padding |
| 盐末位 | `(pos - 5) % 64` | `pos & 0x30` |

UWP 算法 16 次重试全部失败（`pos & 0x30` 只产生 4 种取值，大量落入非法盐）。

**结论**：UWP 已弃用且有缺陷，不可参考。

## 五、服务端错误码语义（实测）

| 场景 | 响应 |
| --- | --- |
| 极简头 / 错误版本 | `403`（WAF 层） |
| 缺 X-Requested-With | `1000 请求方式错误` |
| Token 无效 | `1004 请求未验证` |
| **Token 格式对但内容错** | **`1004 请求验证错误`** |
| 请求成功 | `200 + data` |
| 不存在的路径 | `{"code":404}` |

> 「请求验证错误」里的「验证」指的是 **Token 校验**，不是人机验证。
> 这是本项目最大的误判来源。

## 六、人机验证的真实触发条件（代码确认）

### 拦截器顺序（`NetworkModule.kt:108-118`）

```
RequestSession.capture
  → ApiFailureInterceptor     先执行
  → CaptchaInterceptor        后执行
  → AddCookiesInterceptor     network 层
```

### ApiFailureInterceptor 的放行条件（`ApiFailure.kt:89-101`）

```kotlin
// 唯一放行给验证拦截器的情况
if (body.get("messageStatus")?.asString == "err_request_captcha") {
    return response
}
throw failure   // 其余全部抛异常
```

### err_request_captcha 的实际出现位置

全仓仅三处，**全在写操作**：

| 文件 | 行 | 场景 |
| --- | --- | --- |
| ReplyViewModel.kt | 52 | 发评论 |
| ReplyViewModel.kt | 129 | 发回复 |
| ReplyActivity.kt | 601 | 请求验证参数（带 code/mobile/idcard） |

### 两段式验证（`FeedViewModel.kt:321-341`）

```kotlin
override fun refresh() {
    if (feedState is LoadState.Success) {
        fetchData()                          // 已有内容，正常刷新
    } else {
        fetchFeedData(verifyCaptcha = true)  // 加载失败，带验证重试
    }
}
```

首次失败不弹验证，用户重试时才允许验证。

## 七、可复用的排查顺序（推荐）

如果将来再遇 1004，按这个顺序，不要乱试：

1. **先验证 Token**：用仓库 1 的原版 APK 或独立参考实现算一次，逐字节比对
2. 检查 password 的 Base64 是否保留 padding（本项目踩过的坑）
3. 检查 `appCode` 是否等于 `X-App-Code`（2610291）
4. 检查盐末位算法是否是 `(pos - 5) % 64`
5. 检查盐末尾 4 位残余是否为 0
6. 用真机设备串 / 真机 UA 对比
7. 最后才考虑 TLS 指纹、网络环境

> **不要在 Token 未验证正确的前提下排查其他方向。**
> 本项目为此浪费了大量时间。
