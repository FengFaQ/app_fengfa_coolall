## 1. 需求溯源

用户最初的需求（原话重点）：

> 在根文件夹创建子文件夹 `Kuan`，拉取 c001apk 与 coolapk-desktop 两个仓库，
> **以 C001 作为主项目，以酷安电脑版作为参考**，
> 制作一个酷安第三方客户端，**采取全端通用**，
> 生成安卓端、Windows 端、Linux 端（只检验 Windows 端产物）。

**关键决策变更记录**：

| 时间 | 变更 | 原因 |
| --- | --- | --- |
| 初期 | 曾提出方案 1（Tauri 为主）/ 方案 2（C001 安卓 + Tauri 桌面） | 用户选择方案 3：参考两者自研全端通用 |
| 初期 | 曾讨论 WinUI 3 | WinUI 3 仅支持 Windows，与「全端通用」矛盾，用户改回 Tauri + Vue |
| 中期 | 包名从 `coolall.fengfa.app` 改为 `app.fengfa.coolall` | 原写法不符合 Android applicationId 规范 |
| 中期 | 第一阶段范围收窄为「先只做 Windows」 | 用户确认 |

## 2. 为什么选 Tauri + Vue

**「全端通用」在这两个参考项目之间有两套互斥路线：**

| | 路线 A：以 C001 为主 | 路线 B：Tauri（当前） |
| --- | --- | --- |
| 形态 | Kotlin + Compose | Vue 3 + Tauri 2 |
| 安卓 | 原生 | WebView 容器 |
| Windows/Linux | 需另写一套 | 原生支持 |
| 代码复用 | 0% | 100% |

**Compose 是安卓专属，无法产出桌面端。** 所以「C001 为主 + 全端通用」技术上不成立。
能全端通用的恰好是 coolapk-desktop 那条路线。

C001 的正确价值是：**协议实现的权威参考**。

它的 `TokenV3.kt` 文件头注明 *"Protocol compatibility from coolapk-desktop (MIT)"*，
说明两者 API 协议同源，可交叉验证。

## 3. 协议逆向的核心战役

整个过程是「被拒 → 分析 → 修正 → 前进」的循环：

```
第 1 轮：403 空响应
  → 猜测 IP 被封（错误）
第 2 轮：加分流规则走代理 → 变 567
  → 发现是 EdgeOne 拦截页，不是 IP 问题
第 3 轮：换正确的 UA 格式 + 设备码格式 → 200 + 1004
  → 突破 WAF，暴露下一层
第 4 轮：1004 稳定复现，各种参数组合都无效
  → 确认是服务端强制人机验证
第 5 轮：实现验证码链路
  → 首次有完整的「1004 → 验证 → 重放」集成测试
```

**三条决定性发现**（详见 `02-技术档案.md`）：

1. UA 必须三段式，缺 `(#Build; ...)` 与 `+CoolMarket/...` 尾巴会 403
2. 设备码是 9 段 Base64 反转，不是随机 hex
3. TokenV3 的盐有两条合法性规则，上游只显式处理了一条

## 5. 关键取舍记录

### 5.1 拆分 coolall-core

**决定**：把 device / request / error / token_v3 / captcha 移到独立 crate。

**理由**：`cargo test --lib` 会编译整个 crate 的依赖树。
协议逻辑与 tauri 在同一 crate 时，测试必须装 WebKitGTK 等重型系统库。

**收益**：测试环境从「需要完整桌面环境」变成「零依赖」，41→47 项测试 0.01 秒跑完。

**代价**：多一层 crate 边界。监督者评价「合理，不属于过度设计」。

### 5.2 引入 HttpTransport seam

**决定**：手写 object-safe `BoxFuture` 的 trait，不引入 async-trait。

**理由**：`CoolapkClient` 需保存 `Arc<dyn HttpTransport>`，
而原生 `async fn` trait 不是 dyn-compatible。

**收益**：验证码链路首次可被完整集成测试覆盖。
此前出现过「重放函数写好但没人调用」的假完成状态，正是缺这个测试面导致的。

### 5.3 阶段 1 保留全局单锁

**决定**：接受所有请求串行，阶段 2 再拆分。

**理由**：监督者判断「阶段 1 是正确性问题而非吞吐问题，单锁反而暂时消除了
SESSID 乱序覆盖与 restore 竞态两处隐患」。出包前不做并发重构。

## 6. 团队协作模式

这是**多智能体协作**项目，分工与约定：

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| Lead | 编码、推送、决策、统筹 | 不做长时间轮询 |
| `ci-watcher` | **独占** CI 监控权 | 只写 `docs/CI-DIAGNOSIS.md` |
| `protocol-reviewer` | 协议审查 | 只写 `docs/CODE-REVIEW.md` |
| `frontend-reviewer` | 前端审查 | 只写 `docs/FRONTEND-REVIEW.md` |
| 监督者 | 架构裁决、风险预判 | 只输出报告，不改代码 |

**约定**：

1. 长时间等待一律交给 `ci-watcher`
2. 监督者后台运行，Lead 不等它，继续推进
3. 每轮对话结束必须向监督者同步状态
4. 各智能体写入不同文件，避免冲突
