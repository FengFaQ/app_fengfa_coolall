## 1. 请求为什么被 403 —— 完整因果链

### 1.1 现象演进

| 阶段 | 请求特征 | 响应 |
| --- | --- | --- |
| 裸 curl | 无任何伪装头 | 403，body 空 |
| 加部分 App 头 | 有 `X-App-Id`/`X-App-Version`，UA 残缺 | 567 + EdgeOne 拦截页 HTML |
| UA 补全 + 随机 hex 设备码 | UA 三段式，设备码 `secrets.token_hex(16)` | 403 空 |
| **UA 补全 + 9 段设备码** | 两者都对 | **200 + 业务 JSON** |

### 1.2 两个致命细节

**UA 必须三段式：**

```diff
- Dalvik/2.1.0 (Linux; U; Android 13; MEIZU 21 Pro Build/TKQ1)
+ Dalvik/2.1.0 (Linux; U; Android 13; 2211133C TKQ1.221114.001) \
+   (#Build; Xiaomi; 2211133C; TKQ1.221114.001; 13) \
+   +CoolMarket/16.7.0-2610291-universal
```

实测：缺 `(#Build; ...)` 段或 `+CoolMarket/...` 尾巴，直接 403。

**设备码不是随机 hex：**

```
明文（9 段）：{szlmId}; ; ; ; {maker}; {brand}; {model}; {build}; null
编码：Base64(无padding) → 整体字符串反转 → 去掉换行与 '='
```

随机 hex 会被认出来。且 `TokenV3.create()` 的第一个参数是**编码后的设备串**，
不是 szlmId。

### 1.3 协议版本约束

| 版本 | 结果 |
| --- | --- |
| `16.7.0` / `2610291` | 200 |
| `16.2.0` / `2604201` | 200 |
| `13.4.1` / `2312121` | **403** |

只有 16.x 能过 WAF。实现中不得允许用户降级。

## 2. TokenV3 签名算法

### 2.1 六个步骤

```
1. 查表：index = ((t + appCode) % 100) * 4 + 0x80
         chunk = LOOKUP[index .. index+0x80]        ← 字节切片
         segment = base64_decode(chunk)             ← 还要再解一次！
2. plain    = "com.coolapk.market&{segment}&{md5(device)}&{t}&{appCode}"
3. password = md5(base64_WITH_padding(plain))       ← ⚠️ 保留 '='，本项目踩过的致命坑
4. source   = base64_NO_padding(f"{t:x}/{md5(plain)}")[:22]  ← 这里才去 '='
5. salt     = source[:21] + ALPHABET[(pos(source[21]) - 5) % 64]
6. hash     = bcrypt(password, "$2a$04$" + salt) → 前缀改 $2y
   输出     = "v3" + base64(hash)
```

### 2.2 四个坑

**坑 0（最致命）：password 与 source 的 padding 规则相反**

仓库 1 的 `TokenV3.kt` 里有两个不同的 Base64 函数：

```kotlin
private fun base64(value: String) =
    encoder.withoutPadding().encodeToString(...)        // 去 padding

val password = md5(encoder.encodeToString(plain.toByteArray()))  // 保留 padding
val source = base64("${time.toString(16)}/${md5(plain)}").take(22) // 去 padding
```

`plain` 长度 167 字节，`167 % 3 = 2`，**Base64 必然产生 1 个 `=`**。
用去 padding 的版本做 password，签名就永远错。

**现象**：Token 格式完全合法，服务端返回 `1004 请求验证错误`，没有任何提示。

**坑 1：两层解码**
`LOOKUP` 是 930 字节数组。切片得到 128 字节**之后还要再做一次 base64 解码**，
才得到 96 字符的 `segment`。这是最容易搞错的一步。

**坑 2：盐有两条合法性规则**

| 规则 | 例子 | 说明 |
| --- | --- | --- |
| 末位不能是 `+` | `...ZGJlN+` | `+` 在 ALPHABET 内但不在 bcrypt 字符集 |
| 末尾 4 位残余必须为 0 | `...jI4OR` | 22×6=132 位，16 字节只用 128 位 |

上游靠 `try/except` 捕获 bcrypt 的 `Invalid salt` 遮掩了第二条。
本项目**显式检查**，不依赖异常控制流。

**坑 3：相邻时间戳会收敛**

`create(t)` 与 `create(t+1)` 可能产出**相同 token**——
因为都会跳过非法盐落到同一槽位。

实测：`t=1735689600` 与 `t=1735689601` 输出相同（都跳到 `t+2` 槽位）。
**这不是 bug**，测试时间敏感性必须用间隔较远的时间戳。

### 2.3 LOOKUP 常量位置

```
crates/coolall-core/assets/token_lookup.b64   （1240 字符，解码 930 字节）
```

**不要手工抄写**——抄错一个字符会导致索引错位且极难发现。
本项目的做法是从上游源码程序化提取。

## 3. 游客态 1004

### 3.1 实测矩阵

| 变量 | 试过的取值 | 结果 |
| --- | --- | --- |
| 设备 ID | 32位hex / uuid / 20位字母数字 / 固定hex | 全 1004 |
| SDK 版本 | 30 / 33 / 34 / 35 / 36 | 全 1004 |
| 协议版本 | 16.7.0 / 16.2.0 | 全 1004（13.4.1 是 403） |
| 接口 | feed/list、indexV8、main/init | 全 1004 |
| Cookie 回写 | 维护 cookiejar 重试 6 轮 | 仍 1004 |
| 客户端 | Python urllib / Rust reqwest | 完全相同 |

### 3.2 结论

**1004 与客户端指纹无关，是服务端对未登录请求下发的统一要求。**

必须由真实 WebView 完成人机验证。这就是验证码链路存在的理由。

### 3.3 公开页兜底

```
https://www.coolapk.com/feed/{id}
```

实测：HTTP 200 + 完整 HTML，**无需任何鉴权、不触发验证码**。

注意：`www.coolapk.com/v6/*` 返回 404，公开页只有 HTML 没有 JSON 接口。

**降级顺序很重要**：如果一遇 1004 就抓公开页，用户永远看不到验证入口，
也就永远无法通过验证。本项目用 `allow_public_fallback` 开关控制，
默认关闭，只有用户明确放弃验证时才开启。

## 5. 已证伪的争议：S1「盐检查有致命错误」

**protocol-reviewer 的判断**：
`bits &= (1u64 << nbits) - 1` 把待检查的位清掉了，
导致每个合法盐都被判非法，`create()` 恒返回 `Exhausted`。

**复核结论：不成立。**

### 证据

用 Python 等价复现同一套位运算：

```
盐                            当前     参考     期望
Njc3NDg1ODAvZTk3ZGJlN+       拒绝     拒绝     拒绝     ✅ t+0 末位 '+'
Njc3NDg1ODEvN2RiMjg4OR       拒绝     拒绝     拒绝     ✅ t+1 末4位非0
Njc3NDg1ODIvMmRjMTc4Me       接受     接受     接受     ✅ t+2 合法

穷举 64 个末位字符：当前接受 4 / 参考接受 4 / 不一致 0
```

### 错在哪

`bits &= (1<<nbits)-1` 保留的是**尚未消费的低位比特**，不是把残余清零。
循环结束时残留的正是第 22 个字符的低 4 位。

后续监督者给出了更严谨的等价证明：

```
written == 16 && bits == 0  等价于  第 22 个 bcrypt 字符的索引 < 16
```

**教训**：位运算的静态推演容易出错，必须用可执行代码验证。

## 6. E0255 编译阻塞的完整经过

### 6.1 现象

```
error[E0255]: the name `__cmd__browse` is defined multiple times
  --> src-tauri\src\lib.rs:59:14
   |  ----------------- previous definition of the macro `__cmd__browse` here
59 | pub async fn browse(
```

7 个命令 × 2 个符号 = 14 个 E0255。

### 6.2 错误假设

**Lead 最初判断**：`crate-type = ["staticlib", "cdylib", "rlib"]` 导致同一份代码
被编译多次，宏重复注入。

**实测证伪**：改成 `["rlib"]` 后本地 `cargo check` **仍然报 E0255**。
恢复三类型后反而编译通过。

### 6.3 真正原因

`#[tauri::command]` 会在**模块级宏命名空间**生成 `__cmd__{name}` 与
`__tauri_command_name_{name}`。当这些命令直接定义在 `lib.rs` 里、
而 `lib.rs` 又同时被 `main.rs` 引用时，宏展开冲突。

### 6.4 修法

把 8 个命令函数整体迁到 `src-tauri/src/commands.rs` 子模块，
`generate_handler!` 改成 `commands::browse, ...`。

**这是 ci-watcher 建议的方案，比 Lead 的判断准确。**

## 7. 图标问题

### 7.1 自绘 ICO 是坏的

用 PowerShell 手工封装 PNG-in-ICO 时，目录项写错：

```
数据大小 = 65536
数据偏移 = 177668128    ← 文件总共只有 2733 字节，严重越界
尺寸数   = 1
```

上一轮打包侥幸成功（NSIS 容忍），但这是实质隐患。

### 7.2 监督者的判断不完整

它只看了前 6 字节（reserved=0, type=1, count=1）就判定「合法」，
没有验证目录项偏移是否在文件边界内。

### 7.3 现在的做法

用 Tauri 官方 CLI 生成：

```powershell
cd src-tauri
npx @tauri-apps/cli icon ./icons/icon.png
```

生成 6 个尺寸（16/24/32/48/64/256），全部偏移在边界内。
同时生成 Android/iOS 全套，为后续多端预留。
